# Product Requirements Document — Dynamic Agentic Chat Assistant Platform

**Working title:** Assistant Studio
**Status:** Draft v1 (for build)
**Owners:** 2-person team (+ Claude Code as build assistant)
**Last updated:** 2026-09-02

---

## 1. Summary

A self-hostable, multi-tenant platform where a user assembles their own **Assistant** — a
configurable agentic chat pipeline — by choosing:

- **Data / context sources** (uploaded files, URLs, pasted text) that become a per-Assistant knowledge base (RAG).
- **Database integrations** (Postgres, MySQL, SQLite, MongoDB) with per-connection permissions (read / write / DDL, table allow/deny, row caps).
- **Tools** (web search, HTTP request, calculator, date/time) and **MCP servers** (any stdio / HTTP / SSE MCP server) whose tools become available to the agent.
- **Prompts & rules** — either written by the user or generated by our own AI from a plain-language description of the use case.
- **Model configuration** — Claude model tier per role (router / main / subagent), effort, thinking, turn and cost budgets.
- **Agent behavior** — subagents on/off, human-in-the-loop approval policy, memory settings.

Assistants are authored through three interchangeable surfaces over one config: a **visual
node-graph builder** (drag nodes for knowledge bases, databases, tools, MCP servers,
subagents, guardrails; wire them into the agent), a **guided wizard**, and **form config
panels**. The graph compiles deterministically to the executable config; it is a visual
*configuration* surface, not a fixed execution DAG.

End users then chat with the Assistant. The agent loop is powered by the **Anthropic
Agent SDK (Python)**; our platform dynamically loads the right toolset, retrieval tools,
database tools, and MCP servers per conversation.

**"Dynamic" means two things in v1:** (a) users can connect new data sources, databases,
tools, and MCP servers at runtime without a redeploy; (b) the agent's toolset, prompts,
and model config are composed per conversation from the selected Assistant version.

## 2. Goals & non-goals

### 2.1 Goals (v1)

1. Let a non-expert build a working, grounded chat assistant over their own documents and databases in under 15 minutes.
2. Make every part of the pipeline **configurable and inspectable** — retrieval settings, prompts, tool permissions, model/budget.
3. Ground answers in sources with **citations** the user can verify.
4. Enforce **safety and cost controls**: human approval for risky actions, per-conversation and per-org budgets, tenant isolation, prompt-injection defenses.
5. Ship as a **one-command self-host** (Docker Compose) that also runs fully locally.
6. Provide an **eval harness** so builders can measure and regression-test assistant quality.

### 2.2 Non-goals (v1)

- Multi-LLM-provider support (Anthropic only in v1; provider gateway is post-v1).
- Managed cloud SaaS with billing, SSO/SCIM, marketplace payments (architected for it, not built).
- Connectors requiring OAuth (Google Drive, Notion, Confluence, Slack, GitHub) — post-v1; v1 supports file/URL/text ingestion and token-based MCP servers.
- Fine-grained row-level database access policies (v1 is per-connection permissions).
- Mobile apps; voice; real-time collaboration on the same Assistant config.
- A free-form **dataflow execution engine**. The v1 node-graph builder is a *visual
  configuration surface* — nodes are capabilities and config, edges declare what is wired
  into the agent. The runtime is still the model-driven Agent SDK loop, not a fixed DAG.
  Conditional edges, branching, loops, and custom-code nodes are post-v1.

### 2.3 Success metrics

| Metric | Target (v1) |
|---|---|
| Time to first grounded answer (new user → upload → answer) | < 15 min |
| Retrieval quality on a builder's labeled set (recall@8) | ≥ 0.85 on the reference corpus |
| Answer groundedness (Claude-as-judge rubric, 1–5) | ≥ 4.2 average on the eval suite |
| p95 first-token latency (chat) | < 3.5 s |
| p95 full-answer latency (RAG, no tools) | < 12 s |
| Unapproved risky action executed | 0 (hard requirement) |
| Self-host cold start (`docker compose up` → usable) | < 5 min on a laptop |

## 4. Core concepts / domain model (product view)

- **Organization** — tenant boundary. Contains users (via memberships), assistants, connections, budgets, audit log.
- **User / Membership / Role** — `owner`, `admin`, `member`. Roles gate config changes, connection management, and budget changes.
- **Assistant** — a named agentic pipeline. Has a `draft` config and a series of immutable **Assistant Versions**.
- **Assistant Version** — a full, immutable snapshot of the pipeline config (models, prompt, RAG settings, DB connections referenced, tools, MCP servers, subagents, approval policy) plus the **graph** (node/edge layout) it was authored from. Conversations pin a version so behavior is reproducible.
- **Graph** — the visual node-graph representation of an Assistant: typed nodes (input, guardrail, router, knowledge base, data source, database, tool, MCP server, subagent, agent, memory, output) and edges declaring what feeds the agent. The graph *compiles to* the executable config; the two are kept in sync and both stored on the version.
- **Data Source** — a file, URL, or text blob attached to an Assistant. Ingested into **Documents** → **Chunks** (embedded + full-text indexed).
- **Database Connection** — credentials + engine + permission profile, attached to an Assistant. Encrypted at rest.
- **MCP Server** — a registered external tool server (stdio/HTTP/SSE), attached to an Assistant, with a tool allowlist and approval policy.
- **Tool Integration** — a built-in capability (web search, HTTP, calculator) toggled per Assistant.
- **Conversation** — a chat thread against one Assistant Version. Contains **Messages**, **Tool Calls**, **Approvals**, and **Runs** (one agent turn).
- **Approval** — a pending human decision on a risky tool call, surfaced to the user mid-stream.
- **Budget** — a spend cap scoped to org / assistant / conversation for a period.
- **Eval Suite / Case / Run** — golden inputs + expected outputs + scored results for an Assistant Version.

## 5. Functional requirements

### 5.1 Accounts, orgs, access control

- FR-1: Email/password registration and login; JWT access + refresh tokens; argon2 password hashing.
- FR-2: On first login a user gets a personal Organization; they can create additional orgs and invite members by email (invite link; no email server required for self-host — link is shown in UI/logs).
- FR-3: Roles: `owner` (all), `admin` (manage members, connections, budgets, assistants), `member` (create/edit own assistants, chat). Role checks enforced server-side on every mutating endpoint.
- FR-4: Programmatic API tokens (scoped, hashed, revocable) for calling published Assistants from outside the UI.
- FR-5: Audit log of security-relevant actions (connection created/edited, budget changed, member role changed, approval decided, MCP server added).

### 5.2 Assistant configuration ("build the pipeline")

- FR-6: Create/rename/duplicate/archive an Assistant.
- FR-7: Guided creation wizard: (1) describe the use case → (2) AI proposes a starter config **and a starter graph** (system prompt, guardrail rules, RAG defaults, suggested tools, wired nodes) → (3) user edits any section → (4) attach data/DB/MCP → (5) test in a preview chat → (6) publish a version.
- FR-7a: **Visual node-graph builder** — a canvas where the Assistant is edited as typed nodes and edges (input, guardrail, router, knowledge-base, data-source, database, tool, MCP-server, subagent, agent, memory, output). Users add nodes from a palette, connect them, and open a node to edit its settings via the same config panels used elsewhere ("panels where needed"). Edges declare what is available to the agent (e.g. KB → agent, DB → subagent); they do not define a rigid execution order — the agent loop stays model-driven.
- FR-7b: The graph and the form-based config panels are two views of the same underlying Assistant config; edits in either are reflected in the other. The wizard, the canvas, and the panels can all be used interchangeably.
- FR-7c: Graph validation on save: exactly one agent node and one input/output; every referenced data source / DB connection / MCP server belongs to the same Assistant+org; a subagent node has at least one capability edge; no orphan capability nodes (warn); cycles disallowed. Invalid graphs cannot be published.
- FR-7d: The graph compiles deterministically to the executable `AssistantConfig`; a "view compiled config" action shows the JSON. Publishing snapshots both graph and compiled config onto the version.
- FR-8: **Model config panel** — choose model per role (`router`, `main`, `subagent`) from the allowed Claude models; set `effort`, `thinking` mode, `max_turns`, `max_budget_usd` per conversation.
- FR-9: **Prompt panel** — edit the system prompt and an ordered list of guardrail rules; toggle PII redaction, injection scanning, refusal fallback. "Generate with AI" produces a prompt + rules from the use-case description; user can accept/edit.
- FR-10: **RAG panel** — enable/disable; pick embedder and reranker; chunking strategy (max tokens, overlap); toggle contextual retrieval; retrieval params (dense/sparse top-k, RRF k, rerank top-n, min score); toggle citations.
- FR-11: **Databases panel** — add a connection (engine, host/port/db/user/secret, options, SSL); set permission profile (read / write / DDL booleans, table allow/deny lists, row limit, statement timeout); "Test connection"; refresh introspected schema.
- FR-12: **Tools panel** — toggle built-in tools; per-tool config (e.g. web search `max_uses`, HTTP allowed domains) and approval policy (`auto` / `require` / `deny`).
- FR-13: **MCP panel** — register an MCP server (transport, command/URL, headers/env secrets); health check; discover tools; choose which tools are exposed; per-tool approval policy. Enable/disable/reconnect without editing config.
- FR-14: **Subagents panel** — toggle built-in subagents (retrieval, SQL, research); set their model and max turns.
- FR-15: **Approval policy** — a single policy object with defaults per risk class (DB write, DB DDL, non-GET HTTP, MCP tool, file write). File-write and shell tools are `deny` by default and not selectable in v1.
- FR-16: Config validation on save; publish creates an immutable version with a change note; conversations always run against a published version (preview chat runs against the working draft).
- FR-17: Diff view between two Assistant Versions — both a compiled-config JSON diff and a visual graph diff (added/removed/changed nodes and edges).

### 5.3 Data ingestion & RAG

- FR-18: Upload files (PDF, DOCX, TXT, MD, HTML) up to a configurable size limit; store originals in object storage.
- FR-19: Ingest a URL (single page; readable-content extraction) or pasted text.
- FR-20: Background ingestion pipeline: parse → chunk → (optional) contextual-retrieval prefix via a cheap model → embed → index (vector + full-text). Show per-source status (`pending`/`processing`/`ready`/`error`) with error detail and a retry action.
- FR-21: Re-index a source; delete a source (cascades to its documents/chunks); show counts (documents, chunks, tokens).
- FR-22: Retrieval at query time: hybrid dense + sparse search, RRF fusion, rerank, threshold, top-n; returns chunk text + source metadata (title, URI, page/char span) for citations.
- FR-23: The agent exposes retrieval as tools (`kb_search`, `kb_list_sources`); it decides when and how to search (multi-query allowed), optionally via a retrieval subagent.
- FR-24: Answers include inline citations that link to the source and location; UI renders a sources panel.

### 5.4 Database querying

- FR-25: The agent can introspect schema (`sql_list_schemas`, `sql_introspect`) from a cached snapshot, refreshable by the Builder.
- FR-26: The agent can run read queries via `sql_query` (SQL engines) / `mongo_find` / `mongo_aggregate` (MongoDB). Results are row-capped, type-normalized, and truncated with a note when large.
- FR-27: Query safety: single statement only; automatic `LIMIT` injection; enforced statement timeout; blocklist of dangerous constructs (file access, sleep, catalog dumping, multi-statement, transactions that escalate); use of a least-privilege DB role is documented and recommended.
- FR-28: Writes / DDL are only attempted when the permission profile allows them, and each such call triggers a **human approval** with the exact statement shown.
- FR-29: NL→SQL generation is grounded in the cached schema; the agent shows the SQL it ran alongside results.

### 5.5 Tools & MCP

- FR-30: Built-in tools: `web_search` (Anthropic server tool), `http_request` (SSRF-guarded; non-GET requires approval), `calculator`, `datetime`.
- FR-31: MCP servers: support stdio (run as a sandboxed subprocess with resource limits and no host network by default), HTTP, and SSE transports; secrets for headers/env are encrypted; per-server tool allowlist; per-tool approval policy; health/status visible in the UI; reconnect and enable/disable at runtime.
- FR-32: The agent's `allowed_tools` list is composed per conversation strictly from the Assistant Version config; built-in filesystem/shell tools from the SDK are disabled.
- FR-33: All tool calls (input, output, status, latency, cost) are recorded and visible in the conversation's run trace.

### 5.6 Chat runtime

- FR-34: Streaming chat over SSE: token deltas, tool-call started/finished events, approval-required events, citations, usage/cost, done, error.
- FR-35: Conversations persist; users can resume, rename, and delete their own conversations. History beyond a threshold is summarized to control context size.
- FR-36: Mid-stream **approval**: when the agent requests a risky action, the stream emits an `approval_required` event with the tool, arguments, and risk level; the user approves or denies in the UI; the run continues or the tool is refused. Timeout → auto-deny.
- FR-37: Users can interrupt a running turn.
- FR-38: Per-conversation `max_budget_usd` and `max_turns` are enforced; exceeding aborts the turn with a clear message.
- FR-39: Errors (model refusal, tool failure, timeout) are surfaced clearly; refusal fallback is applied when enabled.

### 5.7 Observability, budgets, evals

- FR-40: Every agent turn produces a trace (model, effort, turns, tokens, cost, duration, tool calls) viewable in-app and exported to the tracing backend.
- FR-41: Usage events (LLM, embedding, rerank, tool) are recorded per org/assistant/conversation for cost reporting.
- FR-42: Budgets: org (daily + monthly), assistant, conversation. Soft warning at 80%, hard stop at 100%. Admin dashboard shows spend by assistant/model.
- FR-43: Rate limiting per IP, per user, per org (configurable).
- FR-44: Eval harness: define suites of cases (input + expected/reference + metadata); run a suite against an Assistant Version; compute retrieval metrics (recall@k, MRR, nDCG) where labels exist and answer scores via a Claude-as-judge rubric; store results; compare across versions; a small suite can gate CI.

### 5.8 Self-host & admin

- FR-45: `docker compose up` brings up API, worker, web, Postgres (with pgvector), Redis, object storage; tracing backend is an optional profile.
- FR-46: All external calls are limited to: Anthropic API, the embedding/rerank provider, user-configured DBs/URLs/MCP servers. A fully-offline mode uses a local embedding model and disables web search.
- FR-47: Documented backup/restore (Postgres + object storage) and upgrade path (versioned migrations).
- FR-48: `.env.example` enumerates every secret; the app refuses to start with default/empty critical secrets.

## 6. Non-functional requirements

| Area | Requirement |
|---|---|
| **Scale (v1 target)** | ~50 concurrent users per deployment, ~10k documents / ~1M chunks per Assistant, low-hundreds of chats/day. Architecture must not preclude 10× via a worker pool and swapping the vector store. |
| **Latency** | p95 first token < 3.5 s; p95 RAG answer (no external tools) < 12 s. |
| **Availability** | Single-node acceptable for v1; no single-writer data loss on restart (persisted sessions, idempotent ingestion). |
| **Security** | Tenant isolation on every query; secrets encrypted at rest (envelope encryption); no secrets in logs/traces; prompt-injection defenses (untrusted-content handling, guardrail hook, separate instruction channel); SSRF and SQL guards; sandboxed stdio MCP. |
| **Privacy** | Decline non-essential cookies by default; no personal data in URLs; user data sent only to services the user configured. Configurable data retention for conversations. |
| **Portability** | Runs on a developer laptop (macOS/Windows/Linux) via Docker; amd64 + arm64 images. |
| **Observability** | Structured logs, OpenTelemetry traces, per-turn agent traces, cost accounting. |
| **Accessibility** | Web UI meets WCAG 2.1 AA for core chat and config flows; full keyboard nav; respects light/dark. |
| **Compliance** | None mandated for v1 beyond good hygiene; design leaves room for audit export and data-deletion APIs. |

## 7. Key user flows

### 7.1 Build an Assistant (Builder)

1. **New Assistant** → enter name + a paragraph describing the use case ("Answer support questions from our docs and our orders database").
2. Platform calls Claude to draft a **starter graph + config**: an agent node wired to a knowledge-base node and a database node, plus system prompt, 4–6 guardrail rules, RAG defaults, suggested tools (web search off, DB on). Builder lands on the canvas with this laid out.
3. **Add data**: drop a data-source node, drag in PDFs / paste a docs URL, wire it into the knowledge-base node. Ingestion runs; the node shows `ready`.
4. **Add database**: add a database node, paste a read-only Postgres connection string, set permissions to read-only in the node panel, test, refresh schema, wire it to the agent (or to a SQL subagent node).
5. **Preview chat**: open the side-by-side preview; ask a few questions; inspect the run trace (which chunks, which SQL) — trace steps highlight the nodes they touched.
6. Tune retrieval (raise rerank top-n in the KB node) and the prompt (agent node); re-test. Switch to the form panels for bulk edits if preferred.
7. **Publish v1** with a note (snapshots graph + compiled config). Share the Assistant link with teammates or mint an API token.

### 7.2 Chat with an Assistant (End user)

1. Open the Assistant, type a question.
2. Response streams; a "Searching knowledge base" then "Running SQL" indicator appears; SQL and sources are inspectable.
3. Agent wants to run an `UPDATE` (Builder allowed writes) → **approval card** shows the statement → user denies → agent explains it can't proceed and offers a read-only alternative.
4. Answer arrives with citations; user expands the sources panel.

### 7.3 Manage spend (Org admin)

1. Dashboard shows month-to-date spend by Assistant and model, plus top conversations.
2. Admin sets a monthly org cap and a per-conversation cap.
3. At 80% the admin gets a banner; at 100% new turns are blocked with a clear message.

### 7.4 Evaluate a change (Builder)

1. Builder creates an eval suite: 30 questions with reference answers; 12 have labeled relevant chunks.
2. Runs the suite against `v1` and a candidate `v2` (higher rerank top-n, Sonnet instead of Haiku for `main`).
3. Sees recall@8 and judge score per version; `v2` improves groundedness +0.4 at +38% cost; Builder publishes `v2`.

## 8. Assumptions & decisions (where "you decide" was requested)

| # | Decision | Rationale |
|---|---|---|
| A1 | **Anthropic-only models in v1**; model *tier* + params user-selectable per role. | The Agent SDK is Anthropic-native; a provider gateway is a large, separable effort. |
| A2 | **Visual node-graph builder** *plus* guided wizard *plus* form config panels for v1 — three interchangeable views over one config. The graph is a visual configuration surface (nodes = capabilities/config, edges = wiring), not a dataflow execution engine; the agent loop stays model-driven. | User wants the visual builder in v1. Keeping the compiled `AssistantConfig` as the single executable contract means the runtime work is unchanged and the canvas is "just" another editor + a graph→config compiler. Adds ~2 weeks of frontend (see plan). |
| A3 | **AI-generated prompts/rules + pipeline recommendation** from a use-case description is a first-class feature. | Directly matches the stated product idea ("generated by our ai itself, based on the usecases"). |
| A4 | **pgvector** as the v1 vector store, behind a `VectorStore` interface. | One fewer service to run; transactional consistency with app data; adequate to ~1M chunks. Qdrant is the documented scale-out swap. |
| A5 | **Voyage AI** embeddings (`voyage-3-large`) + rerank (`rerank-2.5`), pluggable; **local BGE** fallback for offline self-host. | Strong retrieval quality, Anthropic-recommended; offline mode keeps the "fully local" promise. |
| A6 | **Hybrid retrieval** (pgvector dense + Postgres FTS sparse) + RRF + rerank, with optional contextual-retrieval preprocessing. | Best quality/complexity trade-off; all within Postgres. |
| A7 | **MinIO** (S3-compatible) for uploaded originals. | Keeps object storage local and swappable for real S3. |
| A8 | **FastAPI + async SQLAlchemy 2.0**, **Next.js 15 + Tailwind + shadcn/ui**, **Arq + Redis** jobs, **custom JWT** auth. | Matches the confirmed defaults; mainstream, well-supported. |
| A9 | **Langfuse** (optional Docker profile) + OpenTelemetry + structlog for observability. | Self-hostable tracing tuned for LLM apps. |
| A10 | **Envelope encryption** for connection/MCP secrets: per-tenant data key wrapped by a master key from env/secret store. | Standard pattern; no plaintext secrets at rest. |
| A11 | **Timeline ≈ 16 weeks** to a production-leaning v1 for 2 devs + Claude Code, 6 phases (see Implementation Plan), including the node-graph builder. | Estimate; assumes ~1 focused day per weekday each; carries a 30–50% buffer (realistic calendar 16–22 weeks). |
| A12 | HITL approvals resolve **within the streaming request** with a generous timeout; client disconnect cancels the run. | Simplest correct model; avoids a separate durable-workflow engine in v1. |

## 9. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **Prompt injection** via retrieved docs, DB rows, or MCP output | Agent takes unintended actions / leaks data | Treat all tool content as untrusted data; instructions only from the system channel; guardrail hook scans tool inputs the model produces; risky actions gated by approval; per-connection least privilege. |
| **Runaway agent cost** | Surprise bills | Per-conversation `max_budget_usd` + `max_turns`; org daily/monthly caps; cheap router model; effort tuned per role; hard stop + interrupt. |
| **NL→SQL correctness** | Wrong answers stated confidently | Ground in cached schema; show the SQL; read-only by default; row caps; encourage evals; judge rubric penalizes ungrounded claims. |
| **MCP server trust / supply chain** | Malicious or flaky tool server | Sandbox stdio servers (subprocess/container, resource limits, no host net by default); TLS for HTTP; per-tool allowlist + approval; audit every call; curated preset list. |
| **Agent SDK subprocess model** (spawns the Claude Code CLI per session) | Throughput / memory under load | Worker pool with bounded concurrency; reuse `ClaudeSDKClient` per conversation; measured load test; documented path to the direct-API tool runner if needed. |
| **Scope creep on "dynamic everything"** | Slips the timeline | Ruthless v1 cut list (section 2.2); config schema versioned; roadmap captures deferrals. |
| **Vector store scaling past ~1M chunks** | Latency / recall degrade | `VectorStore` interface; HNSW tuning; documented Qdrant migration. |
| **Two-person bandwidth** | Timeline risk | Phased plan with a usable product at each phase; Claude Code for scaffolding, tests, docs; buffer in the estimate. |
| **Secret leakage into traces/logs** | Credential compromise | Redaction middleware on logs and tracing; secrets never in model context; encryption at rest; `.env` validation on boot. |

1. Advanced graph features: conditional/branching edges, loops, custom-code nodes, reusable sub-graphs, and an optional true dataflow execution mode (as an alternative to the model-driven loop).

3. OAuth connectors: Google Drive, Notion, Confluence, Slack, GitHub, Gmail.
4. Scheduled / proactive assistants (cron-triggered runs, digests).
5. Embeddable chat widget + public REST/streaming API with per-Assistant keys.
6. Team collaboration on Assistant configs (comments, review/approve).
7. Row-level / column-level DB access policies; query result PII scrubbing profiles.
8. Qdrant / pgvector-at-scale tuning; sharded corpora.
9. SSO/SCIM, enterprise audit export, data-residency controls.
10. Usage-based billing and a hosted multi-tenant cloud offering.
11. Kubernetes Helm chart; horizontal autoscaling of agent workers.
12. Voice input/output; mobile clients.

## 11. Glossary

- **Assistant** — a user-configured agentic chat pipeline.
- **Assistant Version** — an immutable snapshot of an Assistant's graph + compiled config.
- **Graph** — the visual node/edge authoring representation of an Assistant.
- **Graph compiler** — the deterministic function that turns a valid graph into the executable `AssistantConfig`.
- **RAG** — retrieval-augmented generation; here, hybrid search + rerank over a per-Assistant knowledge base.
- **Contextual retrieval** — prepending a short, model-generated context blurb to each chunk before embedding, to improve recall.
- **RRF** — Reciprocal Rank Fusion; merges dense and sparse result rankings.
- **MCP** — Model Context Protocol; a standard for exposing tools/data to an agent.
- **HITL** — human-in-the-loop; here, mid-stream approval of risky tool calls.
- **Run** — one agent turn (one user message → one assistant answer, possibly many tool calls).
- **Envelope encryption** — encrypting data with a data key that is itself encrypted by a master key.
